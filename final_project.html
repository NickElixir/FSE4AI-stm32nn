Final project: ship a PyTorch extension

You ship a custom PyTorch operation as a proper C++ extension: a wheel a stranger can pip install, tests that prove it, an image that runs it, and a git history that shows the team built it. The op is yours; the engineering is the course. The project is one week of work for a team of three and 40% of the course grade. Everything this page asks for is a tool the nine lectures taught, and the table at the end names the exact place each lecture shows up.

Develop inside the course sandbox. The grading machine is CPU-only Linux, and your op has to run there: on CPU tensors, from the wheel, on a machine that has never seen your laptop. A Dockerfile that starts from the clean course image sees only what the repository contains — packages you installed by hand in lab do not exist there.

Teams

  • 3 students per team. The deadline is on lms.skoltech.ru. One submission per team: one zip, named after one member’s Skoltech login, holding the project directory with its .git directory inside — the history of changes is part of the submission. The grader unpacks that zip fresh, so what is inside the zip is what is graded.
  • Every member needs at least one commit under their own git author email, the same email as in AUTHORS. A member with no commit gets 0 for the project; the other two are still graded.

The op

Pick one tensor-to-tensor operation that is expressible as one line of pure PyTorch. That line is the specification: your C++ must produce the same result, and your tests compare against it. The op is yours — not clamp01, not double, not an op built in class. Examples of the right size:

  • clipped square: x.clamp(-3, 3).square()
  • signed log1p: torch.sign(x) * torch.log1p(x.abs())
  • leaky clip: torch.where(x > 0, x, 0.1 * x)

README.md states the Python name, for example fse_ops.clipped_square, and the formula in words. The grader reads that formula and calls your function on tensors you have never seen.

CPU is required

  • The grading machine is CPU-only Linux. The op checks run first, and they call your op on CPU tensors: a submission whose op does not run on CPU fails them, and nothing after that can rescue it.
  • Build one code path — the C++ kernel for CPU tensors, built by setup.py with CppExtension. There is no device dispatch to write and no second kernel to keep green.

The names can differ — your package, your op, your test files — but the shape and every fact in the comments may not: this tree is the same one the checks of the table below grade.

Tests

At least five pytest tests, all on CPU. The list below is five kinds: each kind needs at least one test, and a kind may have at most two — so your suite holds five to ten tests:

  • the shape of the output
  • the dtype of the output
  • one exact numeric input, compared with the pure-PyTorch specification line
  • a second input that a fake op cannot survive: several values the formula treats differently, so the correct output differs from the input itself and from element to element. For the clipped square, [-5.0, 0.5, 2.0] must give [9.0, 0.25, 4.0] — not the input back (that is a no-op), not one result copied to every position (that is one element computed and reused)
  • the error path: pytest.raises(RuntimeError) on an input your TORCH_CHECK rejects

A failed TORCH_CHECK surfaces in Python as RuntimeError. Your TORCH_CHECK must reject at least one real mistake — a dtype the op does not accept: an op that takes float32 only raises on an integer tensor.

pytest must pass against the installed wheel, not against pip install -e pointed at a laptop checkout. The tests are copied out of the source tree before the run, so the run cannot import the sources instead of the wheel.

The hidden checks

Checks A2 and A3 — 14 points between them — are graded with a small pytest file the grader wrote and your repository has never seen. Nothing else about them is hidden: the whole protocol is on this page, and the only thing you do not know in advance is which values the grader picked. So rehearse it: write the same three calls yourselves and run them against the installed wheel from a fresh venv. If your version of the file passes, the grader’s passes too — the two files differ only in the tensor values.

The setup is this page’s own pipeline: the grader unpacks your zip, builds the wheel as in D1, installs it into a fresh venv with torch from the CPU index as in D2, and runs the grader’s file from a neutral directory. The file imports the function named in your README and makes three calls:

  • A normal-range call. One tensor of a few values inside the range the formula in your README describes. For the clipped square from the examples above, the grader might call clipped_square(torch.tensor([-5.0, 0.5, 2.0])) and expect tensor([9.0000, 0.2500, 4.0000]) — exactly what the specification line x.clamp(-3, 3).square() produces on the same tensor, computed by the grader on the spot. The comparison is exact: torch.equal, value for value, no tolerance.
  • The same values with a leading batch dimension of 4. A tensor of shape (4, …) — four rows of the first call’s shape, for example four copies of it stacked. The op must treat the new leading dimension as just more rows: every row’s result equals the specification line’s result for that row. Same exact comparison.
  • The contract violation. A tensor your README’s rules reject — for an op that takes float32, an integer tensor: clipped_square(torch.tensor([1, 2, 3])). The call must raise RuntimeError, and the traceback must come from the extension — from your TORCH_CHECK in C++, not from a Python if in the wrapper that refuses before the C++ ever runs.

What each call is worth. If either value call is wrong, A3 scores 0 — all ten points: the two value calls are the definition of “the op works”. If the violation call fails to raise, or raises before reaching your C++, A2 scores 0 — all four points. Everything else on this page can be green; these three calls alone decide 14 of the 100.

One warning ties the calls together: the grader compares against the formula line in your README, value for value. A formula vaguer than the op loses — the grader’s values are chosen to expose the gap between what the code does and what the README claims it does.

Wheel, smoke script, image

The proof commands of this section run inside the course container. From the course directory that contains compose.yaml: docker compose up -d, then docker compose exec lab bash. Inside lab that directory is mounted at /course, and your checkout of the team repository sits at /course/team-repo. From the repository directory, the wheel is built and installed into a fresh venv:

python3 -m venv /tmp/build-venv
/tmp/build-venv/bin/pip install torch --index-url https://download.pytorch.org/whl/cpu
/tmp/build-venv/bin/pip wheel . --no-deps -w dist
python3 -m venv /tmp/try-venv
/tmp/try-venv/bin/pip install torch --index-url https://download.pytorch.org/whl/cpu
/tmp/try-venv/bin/pip install dist/*.whl

The proof of the wheel is pytest, run by the venv that holds it:

/tmp/try-venv/bin/pip install pytest
cp -r /course/team-repo/tests /tmp/proj-tests
cd /tmp && /tmp/try-venv/bin/python -m pytest -q /tmp/proj-tests

The last line prints 5 passed — or more.

The wheel name has four fields, dashed: distribution, version, Python tag, platform tag. The Python tag and the platform tag pin a compiled wheel to one interpreter version and one operating system, and the platform tag follows the machine that builds: the lecture’s Apple Silicon lab built linux_aarch64, an Intel or AMD Linux machine builds linux_x86_64. The graded wheel is the one built on the grading machine, and the grading machine is Intel/AMD Linux, so the graded tag is linux_x86_64. Your own lab cannot produce that tag and does not have to. --no-deps keeps torch out of your wheel; every environment installs torch itself, from the CPU index https://download.pytorch.org/whl/cpu.

tools/smoke.sh is the whole proof in one command. It is bash: line 1 is the shebang #!/bin/bash, and you mark it executable once with chmod 755 tools/smoke.sh, so ./tools/smoke.sh runs it. Its steps are joined with &&: && runs the next command only after a clean exit, so the first failing step ends the script — green continues, red stops. The script builds the wheel into dist/, greps the wheel listing for the linux platform tag, installs the wheel into a fresh venv together with CPU torch, imports the function from a neutral directory, calls it once, and prints OK:

#!/bin/bash
python3 -m venv /tmp/smoke-build &&
/tmp/smoke-build/bin/pip install torch --index-url https://download.pytorch.org/whl/cpu &&
/tmp/smoke-build/bin/pip wheel . --no-deps -w dist &&
ls dist | grep linux &&
... &&
echo OK

The ... step is yours to fill, the same arrangement as the venv commands above: a second, fresh venv — one that has never seen the source tree — installs CPU torch and then dist/*.whl, and from /tmp imports your function and calls it on one tensor. The first run is slow: torch downloads once. The last line prints OK, and it prints only when every step before it exited 0 — if the script exits 0, a stranger’s machine is satisfied.

The Dockerfile builds an image that contains CPU torch and your wheel, and docker run on that image executes pytest — green, from the wheel, not from source. Because .dockerignore keeps dist out of the build context, the wheel is not taken from dist/: the image builds it itself, in the two stages of the docker lecture — work fat, ship thin. A builder stage installs torch and runs pip wheel; the final stage installs torch first and your wheel second, copies the tests in, and leaves the compiler behind. The first docker build is slow: the CPU torch wheel downloads once, and the installs take a few minutes — the layer cache keeps it for next time.

FROM ... AS build
WORKDIR /src
RUN python3 -m pip install --break-system-packages torch --index-url https://download.pytorch.org/whl/cpu
COPY . .
RUN python3 -m pip wheel . --no-deps -w /wheels

FROM ...
RUN python3 -m pip install --break-system-packages torch --index-url https://download.pytorch.org/whl/cpu
COPY --from=build /wheels /wheels
RUN python3 -m pip install --break-system-packages /wheels/*.whl
COPY tests /opt/tests
CMD [...]

The three ... are yours to fill, and each is named: the first is the builder’s FROM — the course base image, the one lab runs on — with the stage named AS build; the second FROM starts the final stage from the same base; the CMD is the image’s default command, the exact run docker run proves: ["python3", "-m", "pytest", "-q", "/opt/tests"] — pytest against the installed wheel, pointed at the copied-in tests.

Build and run happen on the laptop, where the daemon lives, from the repository directory:

docker build -t fse-ops:0.1 .
docker run --rm fse-ops:0.1

The container runs the tests against the wheel the image installed; the last line prints 5 passed — or more. A red test exits nonzero, and so does the container.

The project note

Half a page at the end of README.md, or NOTE.md. Three facts, plainly written, each one a grader can check:

  • one real bug the team hit: how it surfaced — a pdb session, a red test, a traceback — and the fix, citing the commit hash where the fix landed; git log --oneline prints the hashes
  • one input shape or case the op does not handle, and what happens instead
  • one measured observation about the op on a large input, measured with python3 -m cProfile, with the command and the number it printed

Timeline

  • Early, well before the deadline: the CPU op returns a tensor on the default branch. Check G3 wants commits spread over at least three different days — a project built in one sitting fails it.
  • Along the way: pip wheel builds from a clean checkout and installs into a fresh venv; the CI file is committed; the image runs pytest.
  • Submission: the last push happens first, then you pack — one zip, the project directory with .git inside — and upload it to lms.skoltech.ru before the deadline. The grader unpacks the zip fresh and grades what is inside; nothing else is handed in.
